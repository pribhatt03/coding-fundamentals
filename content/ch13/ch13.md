# When it breaks

Three modules ago, a statistical test handed you a *list*. Since then you've:

- pulled the p-value out of a t-test, and noticed which test R chose for you
- read loops you didn't write — including one that printed nothing at all
- seen a missing `library()` line produce an error that pointed the wrong way
- worked out a function you'd never met, by trying it

Code breaks in two ways. Sometimes R stops and tells you: that's an error.
Sometimes it carries on and hands you a wrong answer without a word. The
first kind is annoying. The second kind is dangerous.

**Module 13 is about reading the errors R gives you. Module 14 is about
catching the ones it doesn't.**
:::

# 13. Errors that stop you

An error is R telling you what it couldn't do. It may feel like failure, but
it's actually a win: nothing wrong got stored, and the message says where to
look.

In practice, you'll often paste an error into an AI and ask what's wrong.
This module is about doing it well — knowing what to give the AI, and
checking whether its fix really fixed anything.

::: exercise {#ch13-ex01}

## When R can't read your code

The first kind of error is a *syntax* error. Code has to be written exactly
the way R understands it — there's no spell check to correct a missing
comma or bracket. If R can't read a line, none of it runs. When you read the
error, the word "unexpected" is your giveaway.

::: exercise {#ch13-ex05}

## When R starts, then stops

The second kind is a *runtime* error. Here, R could read the code, started
running it, and hit something it couldn't do. Everything before that line
has already run.

## Warnings

A warning is something in between. R finishes the job, but flags something
it thinks you should know about. Warnings are easy to scroll past, and easy
to make disappear without dealing with them.

## Asking for help

::: exercise {#ch13-ex13}

Read the *what*, then the *where* — and remember the *where* is where R
noticed, not always where the mistake is. When you ask for help, give the
error and the lines that led to it. And when a fix makes the message go
away, check that it fixed the problem too.

An error is the good kind of failure: it stops before anything wrong is
stored. Module 14 is about the kind that doesn't stop.
